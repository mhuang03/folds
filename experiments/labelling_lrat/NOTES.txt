LABELLING BOUND BY KERNEL-CHECKED LRAT CERTIFICATES
===================================================

Goal: the finite checks of bound_of_checks (Folds/Labelling.lean, experiments/labelling2/
PROOFS.txt section 2) for t = 3, 4, 5, certified by SAT proofs replayed in the Lean kernel
(decide +kernel; no native_decide, no Lean.ofReduceBool).

RESULT
  t = 3: proved for all N  (Folds/LabellingSAT3.lean: admissible_le_three, lds_exact_le_three,
         descents_exact_le_three: min(lg(N+1), 4) <= des a + 1).
  t = 4: proved for all N  (Folds/LabellingSAT4.lean: admissible_le_four, lds_exact_le_four,
         descents_exact_le_four: min(lg(N+1), 5) <= des a + 1).
  t = 5: NOT done (cost, see below).
  Axioms: propext, Classical.choice, Quot.sound only (#print axioms).

LEAN'S BUILT-IN LRAT CHECKER
  Std.Tactic.BVDecide.LRAT.check / check_sound (Lean v4.35) does not reduce in the kernel on
  real proofs: decide +kernel gets stuck at Std.Tactic.BVDecide.LRAT.Internal.check.go
  (well-founded recursion); it also stores clauses in an Array (O(n) access in the kernel) and
  the assignment in a HashMap.  bv_decide uses it through Lean.ofReduceBool (compiled code).
  Hence a small checker written for the kernel (Folds/LabellingSATCore.lean) with its own
  soundness proof (Folds/LabellingSAT.lean).

DESIGN
  * Checker: literals 2x / 2x+1; assignment = a bitmask Nat (GMP in the kernel); clauses in a
    binary trie keyed by id, given as a literal in the certificate; RUP steps only (CaDiCaL's
    LRAT has no RAT steps here); hints must have smaller ids.  Kernel-accelerated Nat
    primitives used directly (Nat.beq, Nat.land, Nat.shiftRight, ...).
  * Encoding: the CNF is never generated in Lean.  Each input clause used by the proof carries
    a tag (CTag: lo, hi, ord, tot = totalizer, win = window inequality); the kernel recomputes
    the tag's clause over meaningful variables (VarTag: y m u = [c m < u], totalizer outputs
    o m v lo hi i = [i <= #true inputs in [lo,hi)]) and checks it is contained in the
    certificate clause through the variable table.  gen_sound: every valid tag's clause holds
    for every labelling satisfying the checked window inequalities.
  * Certificates are written as strings, turned into terms by the elaborator lsat_cert%
    (raw Nat literals); the kernel checks the resulting term; soundness holds for any Cert.
  * Checks are split into declarations (initial clauses; RUP segments of ~6000 hints; end)
    and combined by Cert.refutes_seg / refutes_end / sound_of_refutes.  The certificate files
    import only Folds.LabellingSATCore (no Mathlib): ~0.8 GB baseline.

PIPELINE (reproducible; certificate .lean files ARE committed, ~0.2 MB for t = 3, ~8 MB for t = 4)
  gen.py      encoding (mirrors Folds.LSAT.gen), CaDiCaL --lrat, lrat-trim, renumbering
  mkfile.py   writes a certificate file (+ noLab theorem text with --nolab=FILE)
  make_t3.sh, make_t4.sh   regenerate the committed files
  env.sh      tool versions (CaDiCaL 3.0.1 c6073042, lrat-trim b30f400f, built from source)
  Proof sizes (trimmed): t = 3: 124..148 steps, ~700 hints per instance.
                         t = 4: 960..2054 steps, 20k..52k hints per instance, ~930k in total.

COST (1 core, this machine)
  t = 3: Folds.LabellingSAT3Certs builds in 15 s, peak < 1 GB.
  t = 4: 8 certificate files, built one at a time (lake build Folds.LabellingSAT4CertsX):
           A (L61, F31-33) 398 s / 2.36 GB peak RSS,  B 230 s / 1.77 GB,  C 228 s / 1.94 GB,
           D 214 s / 2.09 GB,  E 234 s / 2.27 GB,  F 256 s / 2.27 GB,  G 260 s / 1.89 GB,
           H 222 s / 2.12 GB;  total ~34 min of kernel checking, peak < 2.4 GB per file.
           Folds.LabellingSAT4 (assembly) 94 s.  (lake builds files in parallel by default;
           with 4 jobs the peak is about 4 x 2.4 GB.)
  Kernel speed: about 1.3 ms per hint (RUP hint lookup + propagation), plus ~8 ms per input
  clause for the tag check.  Earlier designs: rebuilding the trie per segment and lazily
  decoded lists cost 2-3x more time; a single declaration per certificate reached 9 GB at
  t = 4 (N = 31).

WHY NOT t = 5
  Trimmed proofs without the normalisation symmetry break (which would need a Lean proof):
    L157: 1.9M hints; F63: 11.4M (331k steps), F64: 13.7M, F80: 1.0M, F100: 0.9M,
    F126: 1.0M, F140: 1.6M, F156: 1.3M; 94 full instances N = 63..156, so roughly 150-250M
    hints in total (CaDiCaL+lrat-trim: 20-160 s per instance), with 8k-16k variables (larger
    bitmasks).  At >= 1.3 ms/hint the kernel would need ~4-5 hours for F63/F64 alone and
    on the order of 60-100 hours in total, with up to ~100 MB of certificate text per
    instance.
  An ofReduceBool (compiled) check would be fast but was not done (not wanted as the main
  deliverable; the certificates would have to be generated, not committed).
